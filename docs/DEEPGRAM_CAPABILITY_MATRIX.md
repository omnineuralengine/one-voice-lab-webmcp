# Deepgram Capability Matrix

This matrix is the reviewable source of truth for how Deepgram capabilities map into Deepgram Voice Lab and the Applied Voice Systems Academy. It separates an official API fact from what this repository can actually execute.

Deepgram core discovery, prerecorded STT, batch TTS, authentication, temporary
token, and realtime-boundary claims were rechecked against official Deepgram
documentation on **2026-08-29**. Flux endpoint, model, turn-event, Configure,
and audio claims retain their 2026-07-28 verification basis. Other rows retain
their earlier repository verification basis.
Production implementations must re-check the linked reference because models,
parameters, event schemas, limits, and availability can change.

## Capability evidence status legend

- **Live-verified**: a real bounded capability run completed with retained verification evidence. No capability currently carries this label.
- **Fixture-verified**: automated or deterministic local fixtures validate construction, state, safety, and cleanup without proving a paid Deepgram response.
- **Implemented with deterministic fixtures**: a real repository path plus the
  provider-independent replay/test surface exists, but retained live-provider
  evidence is not present.
- **Manual verification required**: real account, microphone, audible playback, entitlement, or customer-specific validation remains outstanding.
- **Hosted preview**: reserved for a limitation specific to a hosted reviewer deployment. No capability currently carries this label.
- **Local-only**: the capability intentionally runs or persists only in the local browser/runtime.
- **Locked by design**: privileged management or mutation execution is intentionally unavailable.
- **Experimental**: reserved for genuinely unstable exploratory behavior. The
  Flux speculative-orchestration demonstrator carries this label and makes no
  LLM, TTS, or tool call.

The **Executable status** column remains an operational description, not a UI badge or verification claim.

## Security and provenance rules

- `DEEPGRAM_API_KEY` is read only by trusted local server code. It must never enter client props, browser storage, generated code, an inspector envelope, or an export.
- Temporary tokens are held in memory only and are redacted in traces and downloadable artifacts.
- Hosted temporary-token issuance is disabled. A token is not ONE authorization,
  its TTL is not a session/spend bound, and reconnect must obtain fresh admission
  and a fresh token. Provider replay/concurrency/session-binding/revocation
  behavior remains unverified.
- A live response must retain its request ID when Deepgram returns one. Simulated and example data must use local identifiers and a visible provenance label.
- Local simulations do not prove product latency, accuracy, availability, or third-party integration behavior.
- Manage mutations stay disabled. Self-hosted, regional, telephony, and contact-center designs require entitlement and customer-specific validation.
- Generated learning exports contain sanitized configuration and reasoning, not credentials or raw audio by default.
